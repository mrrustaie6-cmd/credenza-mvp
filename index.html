Process

From invisible to underwritable

Four steps, the same for every corridor — only the data adapters underneath change.

01 / Consent

Person opts in

The newcomer chooses exactly which sources to connect. Nothing is pulled without an explicit, revocable grant.

02 / Verify

Signals cross-checked

Verified financial records, guarantors and registries are checked against each other, not taken at face value — on-chain history is one additional signal among these, not the core input.

03 / Score

Trust profile assembled

A single, explainable index is produced — every point is traceable to a specific signal — with a conservative starting limit in low-data corridors.

04 / Issue

Bank queries via API

The destination bank calls Credenza's API at the point of onboarding — no manual paperwork on either side.

Built for verification, not blind trust

Credenza does not ask a bank to trust a score blindly. Each signal behind the index is linked to its source, its verification method and a confidence level. Credenza provides evidence; the bank makes the final underwriting decision.

System design

Architecture, in four layers

No layer stores more than it needs to. The scoring engine never sees raw documents; the bank never sees raw source data.

Layer 1

Consent Layer

Per-source, revocable authorization. Every data pull is logged against an explicit user grant — nothing is fetched by default.

→
Layer 2

Corridor Verification Engine

Source-specific adapters extract and cross-check signals (documents, guarantors, registries, on-chain history) against each other.

→
Layer 3

Trust Scoring Engine

Converts verified signals into a single explainable index, with each contribution traceable back to its source and confidence level.

→
Layer 4

Bank API Layer

Delivers the evidence-backed profile to the destination bank's onboarding or underwriting flow via a versioned REST API.

Data layer is non-custodial by design: Credenza is built to broker verification and consent, not to become a long-term store of applicants' raw financial documents.

Compliance & data posture

Designed around consent, not around access

Principles the architecture is being designed to, ahead of any real integration.

✓

Consent-first by default

No source is queried without an explicit, per-source, revocable authorization from the person.

§

GDPR-aligned handling

Data minimization, purpose limitation and a documented legal basis are treated as design requirements, not an afterthought.

⌘

Non-custodial data layer

Credenza is built to broker and verify, not to become a permanent warehouse of applicants' raw financial documents.

⇄

Evidence, not a black box

Banks receive the signal-level evidence behind the index, and always make the final underwriting call themselves.

Concept note

Why this, why now

Global credit-portability products already exist and already work — banks pay for them. Existing providers have limited practical coverage for sanctioned corridors. Every year, a substantial number of Iranians move to Europe and the Americas carrying real, provable financial discipline that simply has nowhere to land. Credenza is built specifically for that gap, by someone who has spent years navigating it personally as a bank employee inside Iran — not as an outside observer.

This page is a concept demonstration prepared alongside the written business plan for evaluation by Startup Estonia's Startup Committee. No real user data is collected here.

Current status — please read

Credenza is pre-operational. It does not currently have live operational access to real financial data in Iran, or in any other market. Everything on this page — the interactive trust-profile builder, the sample PDF report, the API request/response examples and every score shown — is a mock-up built with illustrative, non-real data to demonstrate the intended product. No applicant data has been collected, verified or scored by Credenza to date.
